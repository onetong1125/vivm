## 1. 范围与结论

依据当前工作区的 Java 后端、JPA 模型、Vue 调用和测试源码制定；工作区有大量暂存、未暂存及未跟踪文件，以当前磁盘内容为准。本次只新增计划与术语表，不改现有源码。

采用模块化单体：保留 Spring Boot、MySQL、Vue 及现有部署方式，将 JPA 迁移为用户指定的 MyBatis-Plus，允许重新设计表关系，按业务能力组织代码。优先收拢业务规则、隔离远程系统、处理状态一致性，再渐进调整持久化关系。当前规模没有足够证据支持微服务、消息总线、事件溯源、独立读库或通用工作流引擎。

本次设计完成标准：每项主要问题有代码依据；给出候选上下文、聚合及规则归属；覆盖远程失败和并发；阶段有依赖、验收和回退边界；未确认的业务语义明确列出。

## 3. 战略设计：两个候选限界上下文

| 上下文 | 定位 | 业务模块 | 拥有的数据与规则 |
| --- | --- | --- | --- |
| Virtual Resource Management（虚拟资源管理） | 核心域，镜像依赖与安全使用是重点；现有备份是低优先级辅助能力 | image、machine、versioning | 镜像、存储池、虚拟机、备份版本、资源归属、可用性与恢复规则 |
| Identity（身份管理） | 通用支撑能力 | identity | 用户、认证、角色、账户管理 |

两个上下文仍在一个应用、一个数据库中。Identity 向资源用例提供主体 ID 与角色；资源归属和具体操作权限由资源上下文负责。跨上下文不传递 JPA User 实体，不通过 User 对象遍历全部资源。

镜像、VM 和版本目前共同依赖镜像可用性与池级还原约束，先保留为同一上下文中的模块。只有出现独立业务语言、独立生命周期或独立团队维护需求，再评估拆成多个上下文。Libvirt、SSH、qemu-img 是外部系统及技术适配器，不单独命名为业务限界上下文。

不因 User 中存在 balance、ossSpace 就创建计费域或配额域：目前只看到字段初始化与管理修改，尚未发现收费和配额决策流程。

## 4. 战术设计：聚合与一致性边界

| 候选聚合根 | 自身负责 | 不纳入聚合的内容 |
| --- | --- | --- |
| Image | 身份、名称、文件结构类型、可见性、池 ID、父镜像 ID、逻辑删除状态；明确的删除/恢复行为 | 全部后代、VM 对象、全部历史版本 |
| VirtualMachine | 身份、名称、类型、镜像 ID、远程 UUID、已观测运行状态 | Image 对象图和用户聚合 |
| BackupVersion | 所属池 ID、名称、描述、时间、固定的备份成员集合 | 当前镜像对象及其可变状态 |
| StoragePool | 池身份、名称、位置、池级操作准入状态 | 池内全部镜像、VM 和版本 |
| User | 身份、角色、账户资料及相关账户规则 | 资源集合；Spring Security 会话对象 |

ImgChild、ImgPool、ImgVm、VersionImg、VersionPool、UserImg、UserVm 首先视为关联表达，保持旧表映射直到数据迁移阶段。只有确实具有独立生命周期和业务行为时，才升级为实体或聚合。不能根据表名数量决定聚合数量。

具体行为归属：

- Image 的 `markDeleted(at)`、`restore()` 保持自身状态合法；能否物理删除依赖 VM 引用、后代及备份关系，由 image 模块的删除策略基于查询事实决定。
- VirtualMachine 的业务行为约束本地状态迁移；实时运行状态取自 Libvirt，数据库只保存观测值。不能用旧数据库状态证明远端已停止。
- BackupVersion 固定本次备份成员；还原是跨聚合用例，不写成 Version 对 Image 的任意 setter 调用。
- 聚合内修改由同一短数据库事务提交；跨聚合流程由 application 编排。共享本地数据库的短元数据提交可以显式覆盖多个聚合，但不能因此将整个池装载成巨型聚合。
- 只对具有规则的组合引入值对象，例如实际用到的磁盘规格、远程资源标识。普通 ID 和字符串不必全面包装。

迁移后的领域模型不带 JPA/MyBatis-Plus 注解，收窄公共 setter，并把行为逐步迁入模型。MyBatis-Plus 的表记录与 Mapper 放在 infrastructure/persistence；仅对实际迁移的聚合编写必要转换，不建立通用映射框架。此次持久化技术替换及多表聚合保存提供了分离领域对象与表记录的实际理由。Spring Security 的 UserDetails 由身份适配器承担。

## 5. 目标代码布局与依赖

建议布局，按用例迁移时逐步创建，不预建空目录：

```text
com.ttt.vivm
├── identity/{web,application,domain,infrastructure}
└── resource
    ├── application           # 创建模板 VM、还原版本等跨模块用例
    ├── image/{application,domain,infrastructure,web}
    ├── machine/{application,domain,infrastructure,web}
    └── versioning/{application,domain,infrastructure,web}
```

StoragePool 初期放在 image 模块；由 image 模块公开池级操作准入能力。resource/application 可以协调三个模块，三个模块不反向依赖它。领域层不依赖 Controller、DTO、Libvirt、JSch 或其他模块的 Repository。

- web：解析请求、边界校验、转换认证主体、调用用例、映射 HTTP 响应。
- application：权限、加载业务事实、调用领域行为、事务边界、执行外部操作并完成结果记录。
- domain：聚合、真实业务规则和必要的领域策略，不拼接 shell/XML。
- infrastructure：MyBatis-Plus、Libvirt、SSH、XML 模板、远程状态解析。

仅在真实外部依赖处建立小接口，例如 VirtualizationGateway、ImageStorageGateway、BackupGateway；暴露“创建 VM”“创建增量镜像”“备份池”等操作，隐藏 XML、命令顺序和远程异常。现有 TemplateService 与 Connector 迁入对应适配器；SSH 执行器作为其内部技术实现。

写侧按实际聚合需要定义 Repository 契约，由 MyBatis-Plus 适配器实现；适配器封装关联保存与必要 SQL，BaseMapper、Wrapper 不进入领域或用例接口。不强制继承 IService/ServiceImpl，不给每张关联表生成 Service。查询侧由查询实现直接返回 DTO 投影。

列表与详情查询可直接查询 DTO 投影，不必装载完整聚合，也不建立独立 CQRS 系统。DTO 不再依赖跨聚合懒加载对象图。

## 6. 首个完整切片：克隆镜像

选择 `/api/imgs/createClone`：已覆盖父镜像、池、外部文件操作、用户关系和元数据保存，且不需要同时迁移所有 VM 生命周期。

目标入口是 `ImageAppService.cloneImage(actor, command)`。保持原有 HTTP 参数和成功响应；web 层把 parentName 转成应用输入，由 AppService 解析父镜像身份。下游传 parentId 与已解析的存储定位，停止从路径反推父镜像名。

执行次序：

1. 边界校验名称与参数，加载父镜像、池及归属，执行已确认的授权与可克隆规则。
2. 短事务取得池操作准入并预留名称、记录本次操作。旧名称接口仍在时保留全局查名兼容限制；内部使用 ID，待调用方支持 ID/池范围后，镜像名称可放宽为池内唯一（见第 10 节）。
3. 调用 ImageStorageGateway 创建增量文件并刷新池。非零退出、断连和超时不能被当作创建成功。
4. 短事务提交 Image 及其必要关联，标记操作完成、释放准入。
5. 外部成功而提交失败时，保留操作记录以供核对；只有确认产物属于本次操作且可以安全删除时才补偿。状态不确定时不自动重放创建命令。

验收：成功只创建一份镜像及正确关联；同名并发只能一个取得执行权；父镜像不合法或无权限时不执行远程命令；外部失败不生成可用镜像；提交失败和进程中断能够定位未完成操作。

## 7. 外部一致性和并发：必须随写用例迁移

`@Transactional` 无法回滚 SSH 文件修改和 Libvirt 操作。采用短数据库事务、同步远程调用和最小持久化操作记录；不引入通用 Saga 框架。

操作记录至少关联操作 ID、类型、目标池/资源、预留名称、执行状态、可识别的远程结果和错误。先覆盖当前迁移的用例，需要什么再增加什么。区分“明确失败”和“远程结果未知”；后者需核对远端状态后才能重试或释放准入。日志中的错误必须向调用者显式返回，成功响应只在最终提交完成后产生。

并发基线采用池级持久化操作准入，优先正确性与实现简洁：短事务原子取得准入，远程调用期间不持有数据库事务。创建、删除、VM 启停、备份及还原等会影响该池约束的入口必须遵守同一协议。不能仅给还原方法加锁，因为启动 VM 的入口仍可绕过它。不同池可以独立执行，同池串行的性能代价在测量后再决定是否细化。

准入须绑定操作 ID；进程崩溃后不能按超时盲目释放，先核对未完成操作。仅靠 JVM synchronized 或聚合乐观锁不能防止远程副作用重复。数据库唯一约束也必须配合远程执行前的名称预留。

还原版本在以下条件全部具备后迁移：

- 版本属于目标池，备份已确认完成，成员信息固定。
- 获取池准入后查询 Libvirt 的相关 VM 状态，确保没有运行中的使用者；实时查询失败则拒绝还原。
- 远程恢复成功后，在短事务中将该池当前镜像集合变更为版本成员对应的状态，保持镜像依赖关系有效。
- 文件恢复成功而数据库提交失败时进入待核对状态，禁止池内冲突操作；依照操作记录完成元数据收敛，不宣称整体已回滚。

用户已确认：以特定 SSH 账号登录的管理员可以绕过应用。上述准入只约束应用内命令，不能为外部并发修改提供互斥保证。应用在破坏性操作前实时核对远端状态；发现状态偏差，显式报告并进入核对流程，不按旧状态继续覆盖。建议管理员操作前把对应池切为维护状态、完成后刷新与核对；这是运维建议，不是对其绕过权限的限制。若管理员不遵循维护约定，则读后发生外部修改的竞态仍然存在，实时查询不能消除它。

用户已确认并发规则：同一可写镜像同一时刻只允许一个 VM 运行；该镜像被写入时，它依赖的全部祖先都不能被写入。具体采用目标镜像独占写占用与全部祖先共享读占用：启动前在同一池准入及短事务下原子取得整组占用，存在冲突则不调用 Libvirt，不能逐个提交导致部分占用。目标镜像有写占用或祖先读占用时拒绝新写者；任一祖先已有写占用时拒绝后代启动。这样同时覆盖“父先运行”和“后代先运行”两种顺序。

占用按操作 ID/VM ID 和镜像 ID 持久化，模式为 READ/WRITE；READ 可共享，WRITE 与任意现有占用冲突。两个兄弟增量可以分别持有自己的 WRITE，并共享祖先 READ。启用本协议前须在无应用内在途操作的切换窗口核对现有运行 VM、建立占用，不能把空占用表当作无人运行。应用检查与管理员旁路之间的保证边界仍如上所述。

启动成功后占用持续到远端确认停止；池级操作准入释放不等于释放运行占用。明确未启动才能撤销预留，启动结果未知时保留待核对。关闭一个 VM 只释放它持有的占用，不能清除其他 VM 的祖先读取占用。该约束与逻辑删除分开：删除父镜像的可见记录可以成立，仍被后代引用的文件必须保留。还原、文件删除等写入/移除内容的操作也必须检查这些占用，不能只保护 VM start。

shutdown 改为正常关机请求；API 表达“请求已受理”（建议 202），记录关机中并保留占用，通过后续状态核对确认停止后释放。客户机可能忽略请求，不能自动升级为 destroy。新增独立 destroy 操作与前端按钮，明确强制断电；destroy 不删除定义，delete/undefine 仍是独立用例。此处是用户授权的行为变更，需要同步修改前端提示与契约测试。[Libvirt 关机语义](https://libvirt.org/html/libvirt-libvirt-domain.html#virDomainShutdown)

当前备份按用户确认保持“不停机、同端、复制全部文件”，不因重构擅自删除或改造成灾备系统。复制期间可阻止应用对镜像集合进行结构变更，但运行中的 VM 仍会写磁盘，所以复制成功不等于文件集合具有同一时点的一致性；未核查脚本前也不能宣称达到崩溃一致性。备份记录区分复制完成与恢复验证结果，界面保留此限制。版本成员记录业务上的活动镜像集合，同时文件清单包含依赖所需的已逻辑删除镜像；还原时不能把所有复制到的父文件都恢复成用户可用镜像。

远程边界还应统一处理命令参数转义、路径输入、退出码、stderr、超时和中断。名称来自用户输入，属于必要校验边界。正常业务代码不增加多层重复空值检查或静默默认值。

## 8. 实施阶段与验收

| 阶段 | 交付 | 验收 / 退出条件 |
| --- | --- | --- |
| P0 行为与规则基线 | 接口清单、关键业务场景、真实表约束核对、脚本契约、剩余规则；目标表草案 | 九项已确认语义纳入基线；区分不停机文件复制与可靠快照；记录旧名称接口兼容点 |
| P1 外部与持久化适配准备 | 提取 Libvirt/SSH 失败契约；引入 Boot 3 对应 MyBatis-Plus Starter，确定迁移事务边界 | 非零退出、超时、断连测试通过；MySQL 上验证 Mapper、显式 SQL、事务回滚；无真实远程调用 |
| P2 克隆镜像纵向切片 | `ImageAppService.cloneImage`、Image 行为、聚合保存、名称预留和操作记录；池准入先接入所有冲突入口 | 第 6 节验收通过；归属、父 ID、池 ID 保存正确；旧入口没有并发绕过通道 |
| P3 VM 生命周期 | VM 迁移 MyBatis-Plus；多 VM 关联与持久化读写占用分离；shutdown/destroy 区分 | 请求关机不提前解锁；兄弟增量可并行；同镜像单写者；祖先和后代写入双向互斥；远程成功、数据库失败可核对 |
| P4 权限与用户删除 | 池授权、公共使用权、私有资源清理、公共资源保留；身份持久化迁移 | 无池权限不能备份/还原；用户撤销访问后无法新建资源；公共资源保留；部分清理失败可追踪恢复 |
| P5 备份适配与收尾 | 低优先级备份兼容迁移、DTO 查询、剩余表迁移、删除 JPA 依赖与旧写入口 | 不停机复制限制明确；还原前查远端 VM；活动成员与依赖文件分开；历史数据、权限、事务回归通过 |

P0 中确认的对象级权限按每个切片落实；VM、版本及用户删除的相关入口在其权限与资源归属规则完成前不能视为阶段验收通过。P2 的准入覆盖是明确的跨入口改动，不能以“小切片”为由遗漏。

测试以用例可观察结果为主：纯领域测试、外部网关替身的用例测试、本机 MySQL 事务/唯一性/并发集成测试、HTTP 契约与鉴权测试。本期使用 Fake 完成创建—克隆—启动—停止—备份—删除—还原闭环；真实 SSH/Libvirt 和专用真实测试池验证延期，不作为本机交付前提，也不能把 Fake 结果写成真实虚拟化验证。

暂不把当前 contextLoads 当作离线基线：SSH Bean 初始化会尝试连接。先隔离真实适配器再运行业务测试。此次设计未运行 Maven 测试，也未连接数据库、Libvirt 或 SSH。

## 9. 数据迁移与回退

先保持已有表和 HTTP 契约，新增字段采用兼容迁移；待新用例稳定后再删除旧关联表示。每个用例切换时只保留一个写入入口，不同时双写两套业务逻辑。

迁移前查询真实数据库的唯一约束、孤儿关联、重复名称、一镜像多 VM、一资源多用户及跨池依赖。JPA 注解不能证明历史数据符合目标模型；发现冲突应报告并制定数据映射，不能静默丢弃。

目标表关系见第 11 节；用户关系不能未经确认合并成单个 ownerId。结构类型与可见性拆分时，显式记录旧 0/1 值的迁移规则：旧 0→BASE/PUBLIC、旧 1→DELTA/PRIVATE 只是现有编码的迁移映射，新写入不再绑定这两个维度。所有结构变更采用版本化 SQL，验证行数、引用完整性及代表性历史备份。

回退以切片为单位：完成或核对在途操作后再切换入口。新增字段和操作记录保留，旧程序若不能识别新的占用协议就不能安全回退写操作。外部磁盘状态不能通过回退数据库或代码恢复；恢复脚本的回退能力须先验证。破坏性删表、删列放在最后独立变更中。

## 10. 已确认语义与名称范围核查

用户已确认：Pool 与一个镜像链强绑定但概念独立；基础/增量和公共/私有是独立维度；镜像允许多 VM 关联但需要并发控制；逻辑删除父镜像可以继续支撑后代；当前备份同端不停机复制全部文件；区分 shutdown/destroy；删除用户保留公共、删除私有资源；引入 MyBatis-Plus 并允许重设计表；池操作需相应授权，特定 SSH 管理员可绕过应用。

随后补充确认：私有镜像不能被其他用户或公共镜像依赖；同一镜像单写者，并且写入期间全部祖先禁止写入。两项已作为硬性领域规则，替换此前的待定建议。

Libvirt 的唯一性不是所有名称都“全局唯一”：

| 名称 | 官方范围 / 当前实现 | 目标约束 |
| --- | --- | --- |
| StoragePool 名称 | 宿主机内唯一 | 当前单宿主机应用保持池名唯一，不新增多宿主机模型 |
| VM 名称 | 宿主机内唯一 | 当前应用保持 VM 名唯一，远端使用 UUID 定位 |
| StorageVol 名称（镜像文件名） | 池内唯一 | `UNIQUE(pool_id, name)`；先迁移 parentName 等歧义接口为 ID/池内定位，再放宽旧应用全局限制 |
| 应用 BackupVersion 名称 | 代码调用自定义脚本，未调用 Libvirt 快照 API；不能套用池/VM 名规则 | 建议 `UNIQUE(pool_id, name)`，需核对脚本目标目录命名后落实；复制目标可用不可变版本 ID 防碰撞 |

依据：[Libvirt 池与卷名称](https://www.libvirt.org/formatstorage.html)、[Libvirt VM 名称](https://www.libvirt.org/formatdomain.html#general-metadata)。版本名的池内唯一是应用设计建议，不是已验证的脚本行为；即使脚本内部使用快照，也须先查明其对象和路径。

## 11. MyBatis-Plus 与目标表关系

使用 `com.baomidou:mybatis-plus-spring-boot3-starter`，版本在实施时与当前 Boot 3.4.3/Java 17 做依赖和集成验证后固定，不同步升级整个技术栈。[官方接入说明](https://baomidou.com/en/getting-started/)

以下是目标关系草案，名称可在迁移 SQL 中保持旧表兼容：

| 表 / 关系 | 目标表达 | 约束与原因 |
| --- | --- | --- |
| pool | ID、名称、链根镜像 ID、操作准入 | 每池绑定一个根，根不得绑定多个池；根必须属于该池。创建池和根的阶段状态显式处理；镜像链可由父关系推导，暂不增建空壳 chain 表 |
| image | pool_id、parent_image_id、结构类型、可见性、生命周期、文件定位 | 父子同池、无环；逻辑删除保留依赖身份。替代 ImgPool、ImgChild；当前创建 API 的每个增量一个父镜像保持不变 |
| vm | image_id、远端 UUID、运行观测状态、操作状态 | 多个 VM 可指向同一 image_id，不能对 image_id 加唯一约束；替代 ImgVm |
| backup_version | pool_id、名称、复制状态 | 替代 VersionPool；不因复制结束宣称恢复一致性 |
| backup_version_image | version_id、image_id、当时活动成员标记、文件定位 | 保留多对多；分开活动成员与仅为依赖而保留的文件，元数据在备份时固定 |
| pool_permission | pool_id、user_id、操作权限 | 对相应池检查实际操作权；初期只定义当前用例需要的权限，不做通用权限引擎 |
| user_image / user_vm | 暂保留现有归属基数 | 用户尚未确认共享所有权语义；访问授权与归属分开，不擅自压成一个 owner_id |
| image_occupancy | image_id、vm_id/operation_id、READ/WRITE | 保存目标写占用及全部祖先读占用；同池准入下原子检查和写入，不能仅凭普通唯一索引表达完整读写互斥 |

根镜像已逻辑删除时仍可标识该池的链；不因为根退出可用集合而删除池。链可分叉，但仍共享一个根。MyBatis-Plus 没有 JPA 的关系级联，聚合保存需在同一事务里显式执行所需 Mapper/SQL，并测试中途失败回滚。

镜像生命周期不用 `@TableLogic`：该插件会自动过滤已删除记录并限制其更新，而项目必须查询已删除祖先并在版本还原时更新它们。使用显式生命周期条件；恢复、完整依赖查询和普通列表分别表达意图。[官方逻辑删除行为](https://baomidou.com/en/guides/logic-delete/)

迁移按持久化写入集合推进：一个已切换用例的全部数据库写入使用同一数据源和明确的 Spring JDBC 事务管理器，不混合依赖 JPA flush 与 Mapper 更新。旧用例可暂留 JPA，但同一业务写入只能经过一个入口；共享准入表的兼容路径须通过真实 MySQL 回滚测试。迁移完成后移除 Spring Data JPA、Hibernate 和旧映射，不长期保留两套持久化。

## 12. 用户删除、权限和剩余决策

`UserAppService.deleteUser` 负责跨身份与资源的编排，实现在 application 包中协调两个领域；Identity 不直接调用资源 Mapper。

1. 标记账户进入删除流程，撤销会话、remember-me 凭据及后续访问资格，禁止创建新资源；资源写入口也检查账户状态，以覆盖已在途请求。
2. 获取该账户的资源与相关池，按实际权限/归属形成处置清单。保留公共资源，解除失效用户授权；公共资源转系统管理是建议，具体管理主体不伪装成已确认规则。
3. 对应删除的私有 VM 先停止再取消定义，明确记录失败；随后处理私有镜像，依据完整依赖从叶向根清理。池内还有保留资源时不能级联删池。停止采用正常关机，未停止则流程保持未完成；不暗中升级为强制断电。
4. 按已确认规则，其他用户/公共镜像依赖该用户私有镜像属于非法关系。新写入从源头禁止；迁移发现历史违规时报告并先修复，不增加“为了其他用户继续保留私有文件”的正常回退分支。同一用户内部的私有依赖按叶到根清理，公共祖先保留；清理中途失败按操作记录继续，不能破坏尚未清理的后代。
5. 所有处置完成后最终删除/匿名化账户资料并保留必要操作记录；部分失败不能返回“删除成功”。具体账户资料保留方式作为实施选择，不增加业务保留期限假设。

公共镜像自由使用不赋予删除镜像、还原整个池的权限。池级管理操作按 pool_permission 判断。由于克隆会在绑定池内创建新资源，“公共镜像使用权是否自动包含在该池创建个人增量镜像”仍需明确；可将 USE_PUBLIC_IMAGE 与 RESTORE_POOL 分开表达，避免要求普通使用者拥有整个池管理权。

镜像授权约束在 `ImageAppService.cloneImage`、VM 使用入口以及任何改变可见性/父关系的入口统一执行：私有父镜像只允许同一归属用户依赖；公共镜像的全部祖先必须公共，不能只检查直接父节点。当前重构不新增发布功能，但如果现有或后续入口支持从 PRIVATE 改 PUBLIC，必须检查完整祖先链；PUBLIC 改 PRIVATE 也须检查已有其他用户/公共后代，不能使既有依赖非法。普通权限校验在应用入口执行，已加载的合法领域事实不逐层重复验证。

尚未闭合的决策仅保留以下项，不重复询问已经确认的九项语义：

- 共享归属资源、公共资源后续管理主体，以及公共使用权包含的池内创建操作范围。
- 备份脚本的真实目录和命名、复制实现；现有备份是否移除未获授权，因此保留低优先级兼容迁移。

新增验收案例：A→B→C 且 B 已逻辑删除仍能使用 C；两 VM 同时申请同一可写镜像只有一个成功；A 写入阻止 C 启动、C 运行阻止 A 写入；B/C 作为兄弟镜像时可共享 A 并行，关闭其中一个不能解除另一个对 A 的占用；shutdown 被忽略时不解锁；用户不能以其他用户的私有镜像创建镜像或 VM；公共镜像不能包含任何私有祖先；删除用户后公共镜像保留、其私有依赖子树清理；清理失败账户不能继续登录；无池操作权不能还原；SSH 管理员改变远端状态后应用能够识别已发生的偏差且不伪报完成。
