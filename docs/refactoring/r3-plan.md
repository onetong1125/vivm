# R3 镜像、池与可见性实施计划

日期：2026-09-24。状态：R3 代码与本机验证完成，2026-11-17 用户批准提交；未进入 R4。实施结果见 [R3 报告](r3-report.md)。依据：R2 提交 `4be25ca`、当前镜像读写代码及用户本次业务澄清。

## 1. 目标和范围

建立独立的镜像/池领域模型、内部依赖查询和按主体授权的镜像列表/详情。R3 交付包括领域规则、MyBatis 查询、HTTP 与前端展示及相应测试。完整克隆/删除写流程属于 R5，运行占用属于 R4/R6，公共管理主体属于权限批次；这些规则不能因为 R3 领域测试通过而被标为端到端已实现。

旧库 `vivm_db` 数据可以舍弃，不执行历史数据清洗或重建数据库。需要测试数据时在独立测试库构造。

## 2. 已确认语义

- 每池绑定一棵单根依赖树；父镜像允许多个子镜像，每个镜像最多一个父镜像，父子必须同池。
- BASE/DELTA、PUBLIC/PRIVATE、ACTIVE/DELETED 分别表达结构、可见性和生命周期。
- 管理员可以查看镜像，但和其他用户一样，不能基于他人私有镜像创建自己的镜像。管理权也不能推导出这种使用权。
- 公共镜像的全部祖先必须公共；私有镜像的私有祖先必须属于同一用户。
- DELETED 祖先可以支撑已有后代，不能被选为新的直接克隆父镜像。
- 普通列表只显示 ACTIVE；普通用户看到公共和自己的私有镜像。管理员在同一列表中仍受 ACTIVE 条件约束；专门的已删除资源管理入口以后按需增加。
- 公共镜像上创建个人增量与备份、恢复、删除整个池是不同操作。公共可见、私有隔离现在落实；公共克隆具体授权条件在 R5 接入写流程前确定，不能默认为必须具有池操作权限。

## 3. 字段与权限职责

| 模型字段/信息 | 含义 | 使用约束 |
| --- | --- | --- |
| `ownerId` | 私有镜像的单一归属用户 | PRIVATE 必须有值；PUBLIC 无私有归属，模型中为 null；账户私有资源清理必须同时匹配 PRIVATE 与 ownerId |
| `createdBy` | 创建来源的用户标识 | 与可见性、归属和管理权限独立；不用于授权或公共资源级联删除；未知来源允许未记录，不猜测创建者 |
| 管理权限 | 对具体资源执行具体管理操作的资格 | 公共创建者不自动获得删除权；R3 不新增管理员或创建者自动获权的规则；最终主体由权限批次确定 |

上述是新模型与后续持久化字段的职责。创建者账户失效后如何保留或匿名化来源记录在 R7 落实；无论选哪种方式，都不能导致公共镜像被级联删除。R3 不仅因术语拆分就引入未被当前写路径维护的新列。

## 4. 模块和查询契约

- cycle 的 `domain/resource/image` 放置 `ImageE`、`StoragePoolE`，三个状态值及 `ImagePolicy`。模型用 ID 表达父、池、归属，不包含 JPA 对象图。
- cycle 定义实际查询需要的 Repository 契约；`ImageCatalog` 提供 `listVisible(actor, search)` 和 `getVisible(actor, imageId)`，返回专用投影。HTTP 将认证主体转换成 ID/角色后调用，不把 Spring Security 对象带入 cycle。
- dao 提供 Mapper、Record、Assembler 与查询实现。新增类按实际使用创建，不为每张旧关联表建立单独领域模型或 Repository。
- 内部祖先查询按指定镜像向上查，包含 DELETED；该查询结果不直接序列化成 HTTP 响应，不为展示列表加载整棵池树。
- 可见性判断和派生资格判断分开。管理员角色只影响查看判断，派生判断始终检查私有归属。R3 的派生资格是领域规则测试面，尚不代表克隆端点的全部授权已经接入。
- 普通用户查询不可见镜像详情返回 404；搜索、列表和任何返回的关联字段都不能泄露不可见分支的名称、ID、归属或数量。R3 的 DTO 不新增 children/descendants 整树展开。
- 现有 `ImgDTO`、`ImgDetailsDTO` 改为查询投影转换；三个独立状态同步进入 `ImagesPage.vue`。旧 `status` 混合锁定含义，不把它改名后冒充运行占用已经实现。

## 5. 过渡读取与写入衔接

当前 V2 只做一次性回填。`ImageService` 创建/删除仍写 `img_type`、`is_delete` 与 `user_img/img_pool/img_child`，`VersionService` 恢复仍写 `is_delete`；这些写流程没有维护新列。直接改读新列会把新建增量误读为默认 BASE/PUBLIC/ACTIVE，或丢失池和父关系。

R3 采用明确的兼容查询实现：结构由现行父关系投影，可见性由现行 `img_type` 投影，生命周期由现行 `is_delete` 投影，池及私有归属从现行关系读取。没有按行在新旧来源之间 COALESCE 的猜测，没有查询时 UPDATE 修复。私有归属缺失或多重等不符合模型的关系须显式暴露，不能默认为 PUBLIC 或选择任意用户。

新模型能够独立表达 BASE/PRIVATE 和 DELTA/PUBLIC；过渡写流程尚不能生成这些组合，领域测试可用构造数据验证，不宣称整个产品已经支持任意组合。PUBLIC 的旧用户关联仅作创建来源参考，不能转换成公共删除权；无法确定唯一来源时不强行推断。

后续 R5/R6/R8 按各自写入集合完成切换，再将查询实现切换为规范字段。只有字段真正由写流程维护后才增加相应约束。撤回上一版 R3 草案中“立即直接读新列并放宽为池内同名”的安排；`parentName` 尚存在时保持应用名称解析无歧义。

已提交的 V1～V3 保持不变。R3 不提前占用原计划留给后续约束收紧的 V4；若实现所需索引确实需要迁移，再依据实际查询添加并同步后续编号，不为可舍弃旧数据制作复杂迁移。

## 6. 验证矩阵

| 场景 | 预期证据 |
| --- | --- |
| 同池单根、多子；BASE/DELTA、跨池父关系 | 纯领域测试验证结构与可见性独立；非法关系被拒 |
| 管理员查看 A 的私有镜像后尝试据此创建自己的镜像 | 查看规则允许；派生领域规则拒绝，不因 ADMIN 豁免 |
| 公共根 P 下 A 的私有分支 A1、B 的私有分支 B1 | A 的列表/搜索只含 P、A1；P 详情不带 B1 的字段或分支统计；直接请求 B1 返回 404；B 的断言对称 |
| 公共镜像的间接祖先为私有 | 完整祖先规则拒绝，即使直接父镜像标为 PUBLIC |
| P → A1(DELETED) → A2(ACTIVE)，A1/A2 同属 A | 内部查询包含 A1；A 的普通列表不含 A1、仍可见 A2；新派生不能选择 A1 为直接父 |
| 公共镜像由 A 创建，B 查询该镜像 | B 可见；createdBy 不授予删除权，公共镜像不被归为 A 的私有清理目标；实际账户删除闭环留 R7 |
| 公共镜像可见，用户没有池备份/恢复权限 | R3 查询仍成功；不据此声明克隆写授权已确定 |
| 现行 Fake 创建基础/增量后立即查询，以及删除/恢复元数据后的查询 | MyBatis 投影反映新写入，不读取 V2 默认值或陈旧回填；只验证已执行的路径，不冒充外部生命周期完整验收 |

`ImagePolicyTest` 验证纯规则；`ImageQueryIT` 使用随机 MySQL 库验证 SQL 和分支隔离；`ResourceAuthorizationTest` 用真实认证主体及 A/B/Admin 数据验证 HTTP，不只检查页面隐藏。R2 的账户测试和 R1 的 Fake 契约继续回归。前端构建只证明编译，字段展示和过滤需另有实际接口/页面证据。

## 7. 实施顺序与完成标准

1. 按上述行为矩阵编写领域测试，实现最小模型与分开的查看/派生规则。
2. 实现兼容 Mapper 投影和内部祖先查询，在 MySQL 上验证分支隔离及当前写后读取。
3. 切换镜像列表/详情至授权查询，更新 DTO 和前端状态展示，执行 HTTP 负向测试。
4. 执行相关回归，逐项记录变更、依据、实际测试结果与未接入写流程的边界，形成 R3 报告。

成功标准：新模型规则可独立测试；可见查询不泄露他人分支；管理员没有私有使用豁免；当前创建/删除/恢复后的查询无新旧字段漂移。完成 R3 后按既定流程等待下一批审批，提交前展示范围与 commit message。
